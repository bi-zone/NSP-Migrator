# Firewall Policies Migrator

## Инсталляция и запуск

Для запуска необходим установленный и запущенный Docker. В Linux/macOS при его отсутствии может быть предпринята попытка автоматической установки; в Windows заранее установите Docker Desktop.

Файл `.env` автоматически создается из `.env.example`, если он отсутствует. Его можно настроить вручную до первого запуска. **Параметры подключения к BI.ZONE NSP задаются в веб-интерфейсе мигратора, в разделе Settings → CSP profiles, а не в переменных окружения.**

### Linux и macOS

Из корня репозитория выполните:

```sh
make up
```

Команда проверит окружение, соберет и запустит PostgreSQL и Streamlit, применит миграции и выведет адрес приложения. Доступные команды: `make` или `make help`.

Если проверка окружения не подходит для вашей конфигурации Docker, запустите стек без нее:

```sh
make up NO_CHECK=1
```

### Windows

Установите и запустите Docker Desktop. Для запуска откройте [`win/start-migrator.cmd`](win/start-migrator.cmd): скрипт запустит необходимые компоненты и откроет приложение в браузере.

Для запуска из PowerShell используйте [`win/migrator-commands.ps1`](win/migrator-commands.ps1):

```powershell
.\win\migrator-commands.ps1 up
```

Справка по командам:

```powershell
.\win\migrator-commands.ps1 help
```

Скрипт также поддерживает `down`, `ps`, `logs`, `doctor`, `test` и `check`. При блокировке скачанного скрипта политикой выполнения PowerShell убедитесь, что доверяете источнику, и при необходимости разблокируйте файл через `Unblock-File .\win\migrator-commands.ps1`.

## Описание

Firewall Policies Migrator предназначен для переноса правил межсетевого экрана из конфигураций сторонних МСЭ в **BI.ZONE NSP**. Инструмент разбирает исходную конфигурацию, формирует унифицированные правила, сопоставляет зоны, адресные объекты и сервисы с объектами целевой системы, проверяет правила на совпадения и покрытие существующими политиками и позволяет импортировать подходящие правила.

На текущем этапе поддерживается **Cisco ASA**. Возможность работы с другими вендорами может появиться в последующих версиях.

Мигратор сохраняет связь унифицированных правил с исходными строками конфигурации, позволяет мигрировать выбранные правила и исправлять неоднозначные сопоставления. История выполненных миграций и их результаты доступны в **Reports**.

## Требования перед началом

Подготовьте:

- текстовый файл конфигурации Cisco ASA (`.cfg` или `.txt`), размером не более **200 МБ**;
- учетную запись BI.ZONE NSP с правами, необходимыми для просмотра и создания правил и, при использовании **Auto-create unresolved**, адресных объектов и сервисов;
- адрес веб-интерфейса BI.ZONE NSP, имя пользователя и подходящий способ аутентификации (пароль и/или клиентский сертификат);
- сведения о целевом проекте (**VPC**) и устройстве либо группе устройств, на которые будут импортированы правила;
- существующие зоны BI.ZONE NSP, подходящие для сопоставления с зонами исходных правил.

Параметры подключения к BI.ZONE NSP **не нужно указывать в переменных окружения мигратора**. После запуска приложения создайте профиль подключения в **Settings → Create CSP profile** и проверьте соединение через **Test connection**.

> **Важно.** Операция **Auto-create unresolved** создает отсутствующие адресные объекты и сервисы, но **не создает зоны**. Если подходящих зон нет, создайте их в BI.ZONE NSP до миграции.

## Общий сценарий работы

1. **Settings** — создание профиля подключения к BI.ZONE NSP (**CSP profile**), настройка учетных данных и сертификата, проверка соединения.
2. **Upload rules** — загрузка конфигурации Cisco ASA; в блоке **Map to canonical** — преобразование конфигурации в унифицированные правила.
3. **Trace** — проверка происхождения правил, их адресных объектов, сервисов и исходных строк конфигурации.
4. **Canonical rules** — просмотр унифицированных правил, выбор правил для переноса и настройка миграции (**CSP profile**, **VPC**, **Migration name**, **Install On** и, для группы устройств, **Policies priority placement**). Нажатие **Generate rules** создает область сопоставления.
5. **Mapped rules** — проверка и исправление сопоставлений зон, адресных объектов и сервисов. Для массовой обработки доступны **Assign zone for all rules** и **Auto-create unresolved**.
6. **Execute rules** — подготовка плана импорта, анализ совпадений и покрытия существующими политиками, затем **Push X rules to SD-WAN** для создания новых правил.
7. **Reports** — просмотр сохраненных результатов миграций, поиск и фильтрация политик, скачивание PDF-отчета.

## Шаг 1. Настройка подключения к BI.ZONE NSP (Settings)

*Для создания профиля подключения выполните следующие шаги:*

1. Откройте раздел **Settings** и разверните **Create CSP profile**.
2. Заполните поля:
   1. **Name** — название профиля для выбора в остальных разделах мигратора.
   2. **CSP URL** — адрес BI.ZONE NSP, например `https://csp.example`.
   3. **Username** — имя пользователя.
   4. **Password** — пароль учетной записи, если используется парольная аутентификация.
   5. **Client certificate (PEM, P12, or PFX)** — клиентский сертификат, если он требуется для подключения. В интерфейсе указано ограничение **200 МБ** на файл.
   6. **Certificate is password-protected** — включите, если сертификат защищен паролем, и заполните **Certificate passphrase**.
3. Нажмите **Create profile**.
4. В списке **CSP profiles** выберите созданный профиль в **Profile to manage** и нажмите **Test connection**.
5. Убедитесь, что появилось сообщение **Connection established**. При успешном подключении интерфейс показывает доступные проекты/VPC.

Для изменения профиля выберите его в **Profile to manage**, скорректируйте данные и нажмите **Save changes**. Поля **New password** и **New client certificate** можно оставить пустыми, чтобы сохранить текущие значения. Для отключения профиля используйте **Deactivate**, для удаления сохраненного пароля — **Remove password**. Для удаления самого профиля установите **Confirm deletion** и нажмите **Delete profile**.

> **Примечание.** В списке профилей отображаются имя, адрес, состояние активности, пользователь, тип аутентификации, наличие пароля и ключа, а также срок действия сертификата. Профиль подключения содержит учетные данные: используйте учетную запись с минимально необходимыми правами.

## Шаг 2. Загрузка конфигурации и преобразование в унифицированную модель (Upload rules)

*Для загрузки конфигурации выполните следующие шаги:*

1. Перейдите в **Upload rules**.
2. Выберите **Vendor** — **Cisco ASA**.
3. Укажите **Source name**, например `asa-hub1-upload`.
4. Загрузите файл в **Upload config file** (формат `.txt` или `.cfg`, до 200 МБ).
5. Нажмите **Upload** и дождитесь сообщения **Upload completed successfully**. Если источник уже существует, может отобразиться **Existing source was reused**.
6. Убедитесь, что в блоке **Map to canonical** указан загруженный **snapshot**, и нажмите **Map**.
7. Дождитесь сообщения **Canonical snapshot ready**. Повторная обработка при наличии готового результата может использовать ранее созданный снимок (**Existing result reused when available**).

Раскрывающийся блок **Session context** содержит служебные идентификаторы источника, загрузки, снимка и следующих этапов. Для обычной миграции вручную редактировать их не требуется.

## Шаг 3. Проверка трассировки (Trace)

Раздел **Trace** позволяет установить, из каких строк исходной конфигурации сформировано конкретное унифицированное правило.

*Для проверки правила выполните следующие шаги:*

1. Перейдите в **Trace** и выберите конфигурацию в поле **Configuration**.
2. При необходимости найдите правило или исходный объект в **Find a rule or source line**; включите **Only with problems**, чтобы ограничить выдачу правилами с проблемами.
3. Выберите правило в **Canonical rule**.
4. Проверьте действие (**PERMIT** или **DENY**), приоритет, источник, назначение, протокол, сервис и состояние правила.
5. Изучите блок **What this rule was built from**:
   1. **Source rule** — исходная строка правила.
   2. **Source, destination, and service** — определения объектов, участники групп, сервисы и связанные строки конфигурации.
   3. **Zones** — данные о зонах, если они определены.
   4. **Problems** — выявленные проблемы нормализации.
6. Для технической диагностики разверните **Technical details**, где отображаются типы сущностей, идентификаторы, номера строк и сведения о нормализаторе.

Отсутствие зон в унифицированном правиле не обязательно означает ошибку нормализации: при дальнейшей подготовке миграции зоны могут потребовать назначения в **Mapped rules**.

## Шаг 4. Выбор правил и настройка миграции (Canonical rules)

*Для создания области сопоставления выполните следующие шаги:*

1. Откройте **Canonical rules** и выберите **Source snapshot**.
2. Просмотрите таблицу правил; используйте **Search**, **Filters** и **Sort** для поиска. По необходимости откройте **Inspect rule**: вкладки **Overview**, **Objects**, **Service** и **Operands** позволяют проверить состав правила. Кнопка **Open Trace** открывает трассировку.
3. Отметьте в таблице правила, которые нужно перенести. Если ни одно правило не выбрано, блок **Migration setup** сообщает **No rules selected yet**.
4. В **Migration setup** заполните:
   1. **CSP profile** — ранее настроенный профиль подключения.
   2. **VPC** — целевой проект BI.ZONE NSP из доступного списка.
   3. **Migration name** — название миграции, например `asa-hub1-batch-01`.
   4. **Install On** — целевое устройство (**DEVICE**) или группа (**GROUP**).
   5. **Policies priority placement (for GROUP only)** — расположение правил относительно политик группы: **PRE** или **POST**. Параметр отображается для выбора группы.
5. Нажмите **Generate rules** и дождитесь сообщения **Rules generated** с `mapping_scope_id`.

> **Важно.** На этапе **Generate rules** создается область сопоставления, а не сами правила в BI.ZONE NSP. Фактический импорт выполняется позднее, в разделе **Execute rules**.

## Шаг 5. Сопоставление правил с BI.ZONE NSP (Mapped rules)

В разделе **Mapped rules** отображаются две синхронизированные таблицы: **Canonical policies** (исходные унифицированные правила) и **Mapped policies** (их представление для BI.ZONE NSP). В **Mapping scope selector (use for debug only)** выберите нужную область сопоставления, если она не выбрана автоматически.

В таблице **Mapped policies** статус **Need mapping: N** показывает количество сущностей, требующих обработки. Предупреждение **N rules of mapping scope need manual fixing** означает, что существуют правила с незавершенным сопоставлением.

### Массовое назначение зон

*Для назначения зон выполните следующие шаги:*

1. Разверните **Bulk actions** → **Assign zone for all rules**.
2. В поле **SD-WAN zone** выберите существующую зону, например `LAN` или `WAN`.
3. В поле **Direction** выберите **SRC zone** для зоны источника или **DST zone** для зоны назначения.
4. Нажмите **Assign zone**. При необходимости повторите процедуру для второго направления.

### Автоматическое создание отсутствующих объектов

Для автоматического создания отсутствующих адресных объектов и сервисов откройте **Bulk actions** → **Auto-create unresolved** и нажмите одноименную кнопку. Созданные сущности автоматически выбираются для соответствующих сопоставлений. **Зоны эта операция не создает.**

### Ручное сопоставление

*Для проверки или исправления сопоставления выполните следующие шаги:*

1. Выберите проблемную строку в **Mapped policies**.
2. В **Mapping details** проверьте отдельно **Source zones**, **Destination zones**, **Source address objects**, **Destination address objects** и **Services**. Слева отображается **Canonical**, справа — **Mapped**.
3. Для адресных объектов и сервисов раскройте результат сопоставления и используйте:
   1. **Candidates** — кандидатов, предложенных мигратором (могут отображаться **Rank**, **Score**, **Auto-map strategy**).
   2. **Assign directly** — непосредственный выбор подходящего объекта BI.ZONE NSP.
4. Убедитесь, что значения сопоставлены корректно. При необходимости проверьте **Source lines** — фрагменты исходной конфигурации.
5. Повторите обработку остальных правил до устранения всех обязательных несопоставленных или неоднозначных сущностей.

В результатах сопоставления могут встречаться `matched`, `matched_manually`, `created_directly`, `ambiguous` и `unresolved`. В интерфейсе также отображаются способы выбора, например `auto_selected`, `auto_created` и `manual_direct`. Первые обозначают результаты обработки сущностей, вторые — механизм выбора объекта; не следует смешивать эти поля.

> **Важно.** При выборе объекта вручную сопоставляйте не только названия, но и фактические IP-адреса, подсети, протоколы и порты. На демонстрационных снимках встречается, например, сервис `tcp/22`, которому сопоставлен объект другого протокола; подобные расхождения требуют исправления до импорта.

## Шаг 6. Проверка и импорт (Execute rules)

*Для проверки правил перед импортом выполните следующие шаги:*

1. Перейдите в **Execute rules** и проверьте `mapping_scope_id`.
2. Дождитесь подготовки плана импорта. Пока выполняется операция, может отображаться **Preparing...**. После завершения появляется `execute_plan_id` и блок **Planned for apply and existing rules matching result**.
3. Проверьте показатели:
   1. **Analyzed rules** — общее количество проанализированных правил.
   2. **Valid for apply** — правила, пригодные для создания.
   3. **Found matched rules on SD-WAN** — правила, которым найдены точные соответствия в BI.ZONE NSP.
   4. **Found covered rules on SD-WAN** — правила, действия которых покрываются существующими политиками.
   5. **Errors through analyze** — количество ошибок анализа.
4. Изучите раскрывающиеся списки **Valid rules**, **Matched exactly rules**, **Covered rules** и **Error rules**. В **Covered rules** сравните предполагаемое правило (**Planned for apply rules**) с действующим (**Rules on SD-WAN**).
5. Если результат соответствует ожиданиям, нажмите **Push X rules to SD-WAN**, где `X` — количество правил, пригодных для импорта.
6. Проверьте блок **Push rules to SD-WAN result**: в нем отображаются подтверждение создания, номер коммита и созданные политики с идентификаторами.
7. В BI.ZONE NSP проверьте порядок, действие, зоны, адреса и сервисы созданных политик, а также примените необходимые для вашей среды процедуры публикации и активации конфигурации.

Кнопка **Reset execute cache** сбрасывает сохраненный результат подготовки; используйте ее только при необходимости повторного анализа.

> **Важно.** **MATCHED** и **COVERED** — результаты анализа существующих правил, а не подтверждение создания новых. В приведенном тестовом сценарии были проанализированы 13 правил: 3 признаны пригодными для импорта, 10 покрыты существующими политиками, а после Push созданы именно 3 правила.

## Шаг 7. Просмотр результатов (Reports)

Раздел **Reports** хранит результаты выполненных миграций.

*Для просмотра отчета выполните следующие шаги:*

1. Перейдите в **Reports**.
2. При необходимости настройте фильтры списка: **Search by migration name**, **Created from**, **Created to**, **Creation date-time sorting**, **CSP profile**, **Project / VPC**, **Install on devices**. Время создания отображается в **UTC**.
3. Выберите нужный отчет в таблице. Отобразится раздел **Report policies**.
4. Используйте фильтры по имени политики (**Search by policy name**), значению объекта (**Search by object value**) и итоговому статусу (**Migration result**).
5. Проверьте действие, зоны, адреса источника и назначения, сервисы, результат миграции и его причину (**Reason**).
6. Нажмите **Download PDF**, чтобы скачать отчет.

В результатах могут встречаться следующие значения:

- **PUSHED** — правило успешно создано в BI.ZONE NSP;
- **MATCHED** — до импорта найдено точное совпадение с существующим правилом;
- **COVERED** — правило покрывается уже существующим правилом;
- **FAILED** — операция создания правила завершилась неуспешно;
- **ERROR** — при обработке правила произошла ошибка.

PDF-отчет включает название миграции, дату создания, профиль CSP, проект/VPC, цель установки, сводку по статусам, приоритеты политик, действия, зоны, адреса, сервисы, результаты и причины. Например, тестовый отчет из интерфейса содержит **6 политик: PUSHED — 4, MATCHED — 1, COVERED — 1**, без ошибок.

## Рекомендации по безопасной миграции

- Начинайте с тестового проекта или устройства; переносите правила небольшими группами.
- Проверяйте не только имена объектов, но и их значения, особенно после ручного сопоставления.
- Для устройства и группы устройств используйте правильную цель **Install On**; для **GROUP** дополнительно проверяйте выбор **PRE/POST**.
- До импорта проверяйте **Matched exactly rules** и **Covered rules**, чтобы избежать дублирования политик.
- После импорта сверяйте созданные политики с исходной конфигурацией, а не полагайтесь только на сообщение об успехе.
- Если использована **Auto-create unresolved**, отдельно проверьте созданные адресные объекты и сервисы.

## Типовые проблемы

### Файл не загружается

Проверьте, что формат файла `.cfg` или `.txt`, размер не превышает 200 МБ и выбран **Cisco ASA**.

### Не удается подключиться к BI.ZONE NSP

Проверьте URL, учетные данные, права пользователя, срок действия сертификата и парольную фразу. В разделе **Settings** выберите профиль и нажмите **Test connection**.

### Не удается выбрать VPC или цель установки

Проверьте профиль CSP и доступность проекта в BI.ZONE NSP. После проверки соединения интерфейс отображает доступные VPC.

### В Mapped rules много Need mapping / unresolved / ambiguous

Назначьте зоны через **Assign zone for all rules**. Адресные объекты и сервисы создайте через **Auto-create unresolved** или сопоставьте вручную в **Mapping details**. При нескольких кандидатах проверьте значения объектов и выберите нужный.

### Зоны не создались автоматически

Это ожидаемое поведение: **Auto-create unresolved** не создает зоны. Используйте существующие зоны либо создайте их в BI.ZONE NSP заранее.

### Execute rules показывает MATCHED или COVERED

**MATCHED** означает найденное точное соответствие, **COVERED** — покрытие существующей политикой. Посмотрите сравнение правил: новое правило может оказаться избыточным.

### После импорта правило работает иначе, чем ожидалось

Проверьте порядок и действие правил, зоны, адресные объекты и сервисы. В **Trace** выясните происхождение унифицированного правила и сравните его с созданной политикой.

## Термины

- **CSP profile** — сохраненный в Settings профиль подключения к BI.ZONE NSP.
- **Source snapshot** — сохраненный снимок загруженной конфигурации исходного МСЭ.
- **Canonical rule** — унифицированное представление правила независимо от синтаксиса исходного МСЭ.
- **Trace** — связь унифицированного правила с исходными строками и определениями объектов.
- **Mapping scope** — область сопоставления выбранных унифицированных правил с сущностями BI.ZONE NSP.
- **Mapped policy** — правило после сопоставления зон, адресов и сервисов.
- **Execute plan** — подготовленный набор правил для анализа и последующего импорта.
- **COVERED** — результат анализа, при котором существующая политика покрывает предполагаемое правило.

## Участие в развитии проекта

Правки документации и исходного кода можно предложить через Pull Request в GitHub или запрос на слияние в GitVerse. Для этого создайте fork репозитория, внесите изменения в отдельной ветке и отправьте предложение на рассмотрение.

### Подготовка изменений

1. Создайте fork и клонируйте его локально:

   ```bash
   git clone <URL_ВАШЕГО_FORK>
   cd <ИМЯ_РЕПОЗИТОРИЯ>
   ```
2. Создайте ветку, например `docs/update-readme`:

   ```bash
   git checkout -b docs/update-readme
   ```
3. Внесите изменения, проверьте `git status`, создайте commit и отправьте ветку:

   ```bash
   git add README.md
   git commit -m "docs: update migrator workflow"
   git push origin docs/update-readme
   ```
4. В GitHub откройте **Pull requests** → **New pull request** (при необходимости **compare across forks**), выберите свой fork и ветку, заполните описание и нажмите **Create pull request**.
5. В GitVerse откройте **Запросы** → **Создать новый запрос**, выберите исходную ветку в своем fork и целевую ветку проекта, заполните описание и отправьте запрос.

При замечаниях ревьюера внесите правки в ту же ветку и отправьте новый commit: существующий Pull Request или запрос на слияние обновится автоматически.

Не смешивайте несвязанные изменения в одном запросе и проверяйте, что все инструкции соответствуют актуальному интерфейсу.
