# Firewall Policies Migrator

## Инсталляция и запуск

1. Скопировать файл `.env.example` как файл с именем `.env`, отредактировать 
   необходимые параметры.
2. В корень проекта положить файл клиентского сертификата для подключения к CSP формата `.
pem`. По умолчанию ожидается файл с именем `client_cert.pem`, имя можно изменить в `.env` 
   файле.
3. Запустить команду через makefile: `make up`, следовать инструкциям установки. 
   Доступные make команды можно посмотреть запустив команды `make` или `make help`.

4. Если уверены, что скрипт некорректно валидирует окружение, то для прямого запуска 
   используйте команду с флагом: `make up NO_CHECK=1`

**Основные пользовательские переменные окружения, которые необходимо задать 
индивидуально под систему:**

```bash
# URL адрес для подключения к CSP
APP_SDWAN_CSP_API_URL=https://your-csp-host.example.com

# Путь к клиентскому mTLS сертификату подключения к CSP внутри docker контейнера 
# (следите за volumes) 
APP_SDWAN_CSP_CERT=/app/client_cert.pem

# Логин и пароль администратора CSP
APP_SDWAN_CSP_USERNAME=your-user
APP_SDWAN_CSP_PASSWORD=your-password

# VPC ID проекта, куда мигрируются правила 
# (список доступных vpc можете найти в браузере через консоль разработчика 
# при логине в систему - ответ на http запрос POST /us/v1/login)
APP_SDWAN_VPC_ID=your-vpc-id

# Пара "доменное имя <-> ip адрес" для передачи в extra_hosts докер контейнера
# (на случай, если домен вашего CSP не резолвится через DNS, а клиентский сертификат
# выписан на доменное имя ресурса; необязательные к заполнению)
APP_SDWAN_CSP_HOSTNAME=your-csp-host.example.com
APP_SDWAN_CSP_HOST_IP=10.10.10.10
```

**Формат клиентского сертификата (для mTLS):**

В текущей версии мигратора поддерживаются клиентские сертификаты только 
формата `.pem`, которые должны содержать пару сертификат+ключ. Если у вас сертификат 
формата `.p12`, то вы можете сконвертировать его в `.pem` формат через утилиту openssl:

`openssl pkcs12 -in certificate.p12 -out certificate.pem -nodes`

## Описание

Firewall Policies Migrator предназначен для переноса правил межсетевого экрана из конфигураций сторонних МСЭ в **BI.ZONE NSP**.

> Текущая версия мигратора поддерживает работу с BI.ZONE NSP версиями **26.1+ 
> (бывш. 1.7.6+)**

Мигратор помогает быстро и контролируемо перенести правила фильтрации в BI.ZONE NSP без ручного переписывания политик. Инструмент разбирает конфигурацию исходного МСЭ, формирует унифицированные правила, сопоставляет их src/dst zones/addresses и services с объектами BI.ZONE NSP, проверяет результат и только после этого позволяет импортировать правила в целевую систему.

На текущем этапе поддерживается миграция правил из конфигурации **Cisco ASA**. В дальнейшем мигратор будет расширен для поддержки других вендоров МСЭ.

Миграция выполняется через управляемый пайплайн:

- загрузка конфигурации исходного МСЭ;
- проверка корректности загруженной конфигурации и подсветка ошибок при их наличии;
- формирование унифицированной модели правил в разделе **Canonical rules**;
- выбор правил для миграции: всех сразу или отдельными группами;
- сопоставление зон, адресных объектов и сервисов с объектами BI.ZONE NSP;
- создание адресных объектов и сервисов с помощью операции **Auto-create unresolved**, если они есть в исходной конфигурации, но отсутствуют в BI.ZONE NSP;
- анализ существующих правил в BI.ZONE NSP, чтобы не создавать дубли;
- импорт только тех правил, которые прошли проверку;
- формирование отчета по выполненной миграции.

Инструмент не является простым «конвертером строк». Он сохраняет связь между исходными строками конфигурации и полученными правилами, позволяет выбрать только нужные правила, вручную исправить неоднозначные сопоставления и проверить, не дублируют ли новые правила уже существующие политики в BI.ZONE NSP.

## Требования перед началом

Перед использованием подготовьте:

- файл с конфигурацией Cisco ASA в текстовом формате, например: `asa-config.cfg` или `asa-config.txt`;
- учетную запись BI.ZONE NSP с правами на просмотр и создание правил МСЭ;
- параметры подключения к BI.ZONE NSP, указанные в переменных окружения мигратора;
- понимание, на какое устройство нужно импортировать правила.

**Важно**

Мигратор может создавать адресные объекты и сервисы с помощью операции **Auto-create unresolved**, если они есть в исходной конфигурации, но отсутствуют в BI.ZONE NSP. Зоны автоматически не создаются.

Если в BI.ZONE NSP уже есть подходящие зоны, сопоставьте их с правилами на этапе **Mapped rules**. Если подходящих зон нет, создайте их в BI.ZONE NSP заранее или используйте предсозданные зоны, если они подходят для сценария миграции.


## Общий сценарий работы

Пайплайн миграции состоит из следующих основных этапов:

1. **Upload** -- загрузка исходной конфигурации или выбор ранее загруженной.

2. **Trace** -- проверка связи между строками исходной конфигурации и унифицированными правилами.

3. **Canonical rules** -- выбор унифицированных правил, которые нужно мигрировать.

4. **Mapping and executing rules** -- сопоставление унифицированных правил с правилами политик BI.ZONE NSP и их составляющих, проверка результата и добавление подготовленных правил в систему управления.

## Шаг 1. Загрузка конфигурации и преобразование в унифицированную модель правил

1. Откройте веб-интерфейс мигратора.

2. Перейдите в раздел **Upload rules**.

3. На вкладке **Configuration file** выберите вендора. На текущем этапе поддерживается миграция из конфигурации **Cisco ASA**.

4. В поле **Source name** задайте понятное имя источника, например:

   ```text
   asa-hub1-upload
   ```

5. Загрузите файл конфигурации в блоке **Upload config file**. Поддерживаемые форматы из интерфейса: `TXT`, `CFG`. Ограничение: до `200 MB` на файл.

6. Нажмите **Upload**.

7. Дождитесь сообщения **Upload completed successfully**. После успешной загрузки мигратор отобразит идентификаторы:

   - `source_id` -- идентификатор загруженного источника;
   - `snapshot_id` -- идентификатор снимка загруженной конфигурации.

8. Проверьте блок **Map to canonical**. До загрузки конфигурации в блоке отображается сообщение **Upload config first, then map it to canonical**. После успешной загрузки в нем появится строка **Uploaded snapshot** с `snapshot_id`.

9. Нажмите **Map**, чтобы преобразовать загруженную конфигурацию в унифицированное представление. После выполнения этого шага мигратор создаст унифицированные правила на основе загруженной конфигурации. Далее снимок конфигурации будет использоваться в разделах **Trace**, **Canonical rules**, **Mapped rules** и **Execute rules**.

## Шаг 2. Проверка трассировки

1. Перейдите в раздел **Trace**.

2. В поле **Source snapshot** выберите снимок загруженной конфигурации.

3. Используйте режимы просмотра:

   - **Line -> Canonical (Primary)** -- показывает, в какое унифицированное правило попала выбранная строка исходной конфигурации;
   - **Canonical -> Lines** -- показывает, из каких исходных строк собрано выбранное унифицированное правило.

4. Откройте интересующее правило и проверьте его состав:

   - action;
   - priority;
   - source/destination zones;
   - source/destination objects;
   - services;
   - связанные исходные строки.

Этот этап нужен для проверки смысла правила. Если правило получилось неожиданным, используйте трассировку, чтобы понять, какие строки исходной конфигурации повлияли на результат.

## Шаг 3. Выбор унифицированных правил для миграции

1. Перейдите в раздел **Canonical rules**.

2. Выберите нужный **Source snapshot**.

3. Проверьте таблицу унифицированных правил. В таблице отображаются rule ID, приоритет, имя, зоны, объекты, сервис, действие, состояние правила и секция исходной конфигурации.

4. При необходимости нажмите **Open Trace**, чтобы вернуться к трассировке выбранного правила.

5. Отметьте флажками правила, которые нужно перенести. Необязательно переносить все правила сразу. Безопаснее мигрировать правила небольшими группами: так проще проверять сопоставления и результат импорта.

6. В блоке **Migration setup** заполните:

   - **Migration name** -- имя миграции, например:

      ```text
      asa-hub1-batch-01
      ```

   - **Install On** -- устройство, на которое будут установлены правила.

7. Проверьте выбранное правило в блоке **Rule context inspector**. В нем можно посмотреть зоны, объекты, сервисы и операнды правила до генерации сопоставленных правил.

8. Нажмите **Generate rules**.

После успешной генерации появится сообщение с `mapping_scope_id`, а интерфейс предложит перейти в раздел **Execute rules** или продолжить работу через **Mapped rules**.

## Шаг 4. Сопоставление правил с конфигурацией BI.ZONE NSP

### Проверка и массовое сопоставление сущностей

1. Перейдите в раздел **Mapped rules**.

2. Проверьте значение в поле **Mapping scope selector**. По умолчанию в поле выбрана область сопоставления, созданная на предыдущем шаге в разделе **Canonical rules** после нажатия **Generate rules**. Меняйте значение в **Mapping scope selector** только при необходимости, например если нужно открыть другую ранее созданную область сопоставления.

3. Проверьте предупреждение сверху страницы. Если отображается сообщение вида `N rules of mapping scope need for manual fixing`, значит часть сущностей не удалось сопоставить автоматически или требуется ручной выбор одного из найденных кандидатов.

4. Используйте боковое сравнение:

   - слева -- **Canonical policies**;
   - справа -- **Mapped policies**.

5. Проверьте статус правил в таблице **Mapped policies**:

   - **OK** -- правило сопоставлено и не требует ручной обработки;
   - **Need mapping: N** -- в правиле осталось `N` сущностей, которые нужно сопоставить вручную или создать через **Auto-create unresolved**.

6. Проверьте статусы отдельных сущностей:

   - `matched` -- сущность найдена в каталоге BI.ZONE NSP автоматически;
   - `matched_manually` -- сущность выбрана пользователем вручную;
   - `created_directly` -- сущность создана мигратором напрямую;
   - `ambiguous` -- найдено несколько подходящих кандидатов, требуется выбрать нужную сущность вручную;
   - `unresolved` -- подходящая сущность не найдена, требуется ручное сопоставление или создание сущности.

7. Для массовой обработки используйте блок **Bulk actions**:

   - **Assign zone for all rules** -- назначить зоны для правил;
   - **Auto-create unresolved** -- создать и автоматически выбрать неразрешенные адресные объекты и сервисы на стороне BI.ZONE NSP.

**Важно**

**Auto-create unresolved** не создает зоны. Если у правил не сопоставлены зоны, назначьте их с помощью операции **Assign zone for all rules** в блоке **Bulk actions**.

### Назначение зон

Если у правил не сопоставлены зоны, назначьте их массово:

1. Перейдите в раздел **Mapped rules**.

2. В блоке **Bulk actions** выберите **Assign zone for all rules**.

3. Укажите зоны для правил, у которых не сопоставлены **Source zones** или **Destination zones**.

4. Примените назначение зон.

После выполнения операции проверьте, что у выбранных правил заполнены исходная и целевая зоны.

### Сопоставление адресных объектов и сервисов

Адресные объекты и сервисы можно сопоставлять точечно в карточке конкретного правила:

1. Откройте проблемное правило в **Mapped rules**.

2. Перейдите к блоку **Mapping details**.

3. Проверьте разделы с адресными объектами и сервисами:

   - **Source address objects**;
   - **Destination address objects**;
   - **Services**.

4. Найдите сущность со статусом `unresolved` или `ambiguous`.

   - `unresolved` означает, что мигратор не нашел подходящую сущность в BI.ZONE NSP;
   - `ambiguous` означает, что мигратор нашел несколько возможных кандидатов и требуется выбрать корректный вариант вручную.

5. Используйте один из способов сопоставления:

   - **Candidates** -- выбрать подходящую сущность из предложенных кандидатов;
   - **Assign directly** -- найти сущность в каталоге BI.ZONE NSP вручную.

6. В поле поиска введите имя или часть имени объекта, например:

   ```text
   echo reply
   ```

7. Выберите подходящий объект или сервис из списка и примените сопоставление.

8. Повторяйте действия, пока в области сопоставления не останется сущностей со статусами `unresolved` и `ambiguous`. Пока в области сопоставления есть хотя бы одна такая сущность, мигратор не позволит перейти к проверке и импорту правил.

## Шаг 5. Проверка перед импортом

1. Перейдите в раздел **Execute rules**.

2. Проверьте значение `mapping_scope_id`. Оно должно соответствовать области сопоставления, созданной на предыдущем шаге.

3. Если в поле `execute_target_id` отображается значение `None`, нажмите **Prepare execute target**.

4. Дождитесь формирования набора правил для проверки. После успешного выполнения операции в поле `execute_target_id` появится идентификатор подготовленного набора правил, а на странице отобразится блок **Planned for apply and existing rules matching result**.

5. Проверьте блок **Planned for apply and existing rules matching result**. В нем отображаются ключевые метрики:

   - **Analyzed rules** -- сколько правил проанализировано;
   - **Valid for apply** -- сколько правил можно импортировать;
   - **Found matched rules on SD-WAN** -- сколько правил уже найдено в BI.ZONE NSP как совпадающие;
   - **Found covered rules on SD-WAN** -- сколько правил покрывается существующими правилами;
   - **Errors through analyze** -- сколько правил содержит ошибки анализа.

## Шаг 6. Импорт правил в BI.ZONE NSP

Когда проверка завершена и в списке остались только правила, которые действительно нужно создать:

1. На странице **Execute rules** нажмите **Push X rules to SD-WAN**, где `X` -- количество правил, готовых к импорту.

2. Дождитесь завершения операции.

3. Откройте BI.ZONE NSP.

4. Перейдите к политикам выбранного устройства.

5. Проверьте, что импортированные правила появились в списке политик.

После импорта обязательно проверьте:

- порядок правил относительно существующих политик;
- action правила;
- source/destination zones;
- source/destination address objects;
- service;
- состояние правила;
- отсутствие лишних дублей.

## Рекомендации по безопасной миграции

- Не импортируйте правила напрямую в промышленную среду без проверки на тестовом устройстве или в тестовом проекте.
- Переносите правила небольшими пачками, а не всей конфигурацией сразу.
- Перед нажатием **Push X rules to SD-WAN** проверяйте все блоки на странице **Execute rules**.
- Не игнорируйте `matched exactly` и `covered` -- они помогают не создавать дубли и не ломать существующую логику политик.
- Проверяйте порядок правил после импорта: даже корректно сопоставленное правило может работать иначе, если оказалось не в том месте списка.
- Все сущности со статусами `unresolved` и `ambiguous` нужно разобрать до проверки и импорта правил. Если в области сопоставления останется хотя бы одна такая сущность, мигратор не позволит провалидировать и применить политики.
- Если мигратор автоматически создал объекты или сервисы, проверьте их имена и значения в BI.ZONE NSP после импорта.

## Типовые проблемы

### Файл не загружается

Проверьте, что файл имеет поддерживаемый формат `TXT` или `CFG` и не превышает ограничение по размеру. Также убедитесь, что выбран правильный **Vendor**.

### В Mapped rules много unresolved или ambiguous

Это нормальная ситуация для миграции сложных конфигураций.

Если не сопоставлены зоны, используйте **Assign zone for all rules** в блоке **Bulk actions**. Зоны не создаются автоматически через **Auto-create unresolved**.

Если не сопоставлены адресные объекты или сервисы, используйте **Auto-create unresolved** для автоматического создания неразрешенных сущностей или выполните точечное сопоставление в блоке **Mapping details**.

Если у сущности статус `ambiguous`, выберите корректный вариант вручную из списка кандидатов.

### Зоны не создались автоматически

Так и должно быть: зоны не создаются через **Auto-create unresolved**. Создайте зоны в BI.ZONE NSP заранее или назначьте существующие зоны через **Assign zone for all rules** в разделе **Mapped rules**.

### Execute rules показывает matched exactly

Это означает, что похожее или идентичное правило уже найдено в BI.ZONE NSP. Проверьте детали перед импортом, чтобы не создать дубль.

### Execute rules показывает covered rules

Это означает, что новое правило может быть покрыто уже существующей политикой. Проверьте порядок и смысл правил: возможно, импорт такого правила не нужен.

### После импорта правило работает не так, как ожидалось

Проверьте порядок правил, зоны, адресные объекты и сервисы в BI.ZONE NSP. Затем вернитесь в мигратор и через **Trace** проверьте, из каких строк исходной конфигурации было собрано унифицированное правило.

## Термины

**Снимок конфигурации** -- сохраненное состояние загруженной конфигурации исходного МСЭ. Используется на следующих этапах миграции.

**Унифицированное правило** -- промежуточное представление правила, не зависящее от синтаксиса исходного МСЭ. Оно описывает смысл правила: действие, зоны, адресные объекты, сервисы и связанные параметры.

**Трассировка** -- связь между строками исходной конфигурации и унифицированными правилами, которые были получены после разбора конфигурации.

**Область сопоставления** -- набор выбранных унифицированных правил и их сопоставлений с объектами BI.ZONE NSP.

**Сопоставленное правило** -- правило после привязки унифицированных сущностей к зонам, адресным объектам и сервисам BI.ZONE NSP.

**Набор правил для проверки и импорта** -- подготовленные правила, которые мигратор анализирует перед импортом в BI.ZONE NSP.

## Участие в развитии проекта

Вы можете предложить правки или доработки через Pull Request в GitHub или запрос на слияние в GitVerse.

Такой способ подходит, если у вас нет прав на запись в основной репозиторий. Вы создаете собственную копию репозитория, вносите изменения в ней, а затем отправляете запрос на включение этих изменений в основной проект. После проверки команда проекта примет или отклонит предложенные изменения.

### Подготовка изменений

1. Откройте основной репозиторий проекта.

2. Создайте fork репозитория. Fork — это ваша копия основного репозитория. Изменения сначала вносятся в fork, а затем отправляются на проверку в основной репозиторий.

3. Склонируйте fork на локальный компьютер:

   ```bash
   git clone <URL_ВАШЕГО_FORK>
   cd <ИМЯ_РЕПОЗИТОРИЯ>
   ```

4. Создайте отдельную ветку для изменений:

   ```bash
   git checkout -b docs/update-readme
   ```

   Используйте понятное имя ветки, например:

   ```text
   docs/update-readme
   fix/upload-validation
   feature/vendor-adapter-description
   ```

5. Внесите изменения в файлы проекта.

6. Проверьте измененные файлы:

   ```bash
   git status
   ```

7. Добавьте измененные файлы в commit:

   ```bash
   git add README.md
   ```

   Если нужно добавить все измененные файлы:

   ```bash
   git add .
   ```

8. Создайте commit:

   ```bash
   git commit -m "docs: update contribution guide"
   ```

9. Отправьте ветку в свой fork:

   ```bash
   git push origin docs/update-readme
   ```

После этого можно создать Pull Request или запрос на слияние из ветки вашего fork в основной репозиторий проекта.

### Создание Pull Request в GitHub

1. Откройте свой fork на GitHub.

2. Перейдите на вкладку **Code**.

3. Если GitHub показывает баннер **Compare & pull request** для недавно отправленной ветки, нажмите **Compare & pull request**. Если баннер не отображается:

   1. Перейдите в основной репозиторий проекта.
   2. Откройте вкладку **Pull requests**.
   3. Нажмите **New pull request**.
   4. Нажмите **compare across forks**.

4. Проверьте направление Pull Request:

   - **base repository** — основной репозиторий проекта;
   - **base branch** — ветка основного репозитория, в которую нужно внести изменения, например `main` или `master`;
   - **head repository** — ваш fork;
   - **compare branch** — ветка в вашем fork, в которой вы внесли изменения.

5. Проверьте список изменений на странице Pull Request.

6. Заполните название Pull Request.

   Название должно коротко описывать изменение, например:

   ```text
   docs: update README contribution guide
   ```

7. В описании Pull Request укажите:

   - что изменено;
   - зачем это изменено;
   - как проверить результат;
   - есть ли ограничения или незавершенные части.

   Пример описания:

   ```text
   ## Что изменено

   Добавлена подробная инструкция по созданию Pull Request из fork.

   ## Зачем

   Чтобы пользователи могли предложить правки без дополнительного поиска инструкций.

   ## Как проверить

   Открыть README.md и проверить раздел "Участие в развитии проекта".
   ```

8. Нажмите **Create pull request**.

После создания Pull Request команда проекта сможет посмотреть изменения, оставить комментарии, запросить доработки, принять или отклонить Pull Request.

### Создание запроса на слияние в GitVerse

1. Откройте свой fork в GitVerse.

2. Перейдите на вкладку **Запросы**.

3. Нажмите **Создать новый запрос**. Если после отправки ветки GitVerse показывает баннер с предложением создать запрос на слияние, можно нажать **Создать запрос на слияние** прямо в этом баннере.

4. Заполните направление запроса:

   - **Исходный репозиторий** — ваш fork;
   - **Ветка исходного репозитория** — ветка в вашем fork, в которой вы внесли изменения;
   - **Целевой репозиторий** — основной репозиторий проекта;
   - **Ветка целевого репозитория** — ветка основного репозитория, в которую нужно внести изменения, например `main` или `master`.

5. При необходимости назначьте ревьюеров.

6. Заполните название запроса. Название должно коротко описывать изменение, например:

   ```text
   docs: update README contribution guide
   ```

7. В описании запроса укажите:

   - что изменено;
   - зачем это изменено;
   - как проверить результат;
   - есть ли ограничения или незавершенные части.

   Пример описания:

   ```text
   ## Что изменено

   Добавлена подробная инструкция по созданию запроса на слияние из fork.

   ## Зачем

   Чтобы пользователи могли предложить правки без дополнительного поиска инструкций.

   ## Как проверить

   Открыть README.md и проверить раздел "Участие в развитии проекта".
   ```

8. Нажмите **Создать запрос**.

После создания запроса команда проекта сможет посмотреть изменения, оставить комментарии, запросить доработки, принять или отклонить запрос.

### Доработка Pull Request или запроса на слияние

Если команда проекта попросила внести изменения:

1. Перейдите в локальную копию вашего fork.

2. Переключитесь на ветку, из которой был создан Pull Request или запрос на слияние:

   ```bash
   git checkout docs/update-readme
   ```

3. Внесите нужные изменения.

4. Создайте новый commit:

   ```bash
   git add .
   git commit -m "docs: address review comments"
   ```

5. Отправьте изменения в свой fork:

   ```bash
   git push origin docs/update-readme
   ```

После отправки новых commit они автоматически появятся в уже созданном Pull Request или запросе на слияние. Создавать новый запрос не нужно.

### Рекомендации к изменениям

- Делайте изменения в отдельной ветке, а не в `main` или `master`.
- Не смешивайте в одном Pull Request разные типы изменений, например исправление опечаток и доработку логики мигратора.
- Используйте понятные названия веток и commit.
- Перед отправкой проверьте, что в Pull Request или запрос попали только нужные файлы.
- Если изменение связано с документацией, проверьте, что текст читается последовательно и не содержит временных комментариев.
